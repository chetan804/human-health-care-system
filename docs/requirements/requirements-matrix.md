## Critical acceptance rules and unresolved contracts

### AUTH — identity and scoped authorization (§§11–12, 51–55)
- Public registration must never grant a staff, administrator, auditor or infrastructure role. Staff onboarding and initial privileged bootstrap need approved operator procedures.
- Roles are resolved from authoritative server state and facility membership, not client role claims. Authentication is not authorization. A valid token alone never establishes patient access.
- Patient self-access needs a verified user–patient linkage. Email/name matching alone cannot establish that linkage.
- Every resource lookup, list/search, export, background action and idempotent replay must enforce scope. Test cross-organization IDs, cross-facility IDs, stale memberships and reassignment.
- Refresh credentials are hashed at rest, rotated atomically, and grouped into revocable sessions. Replay revokes the affected token family. Logout and account disable must invalidate continuing access within an approved maximum window.
- Recovery responses must not enumerate accounts. Reset and verification tokens are short-lived, single-use and hashed; sensitive tokens must not appear in URLs or ordinary logs.
- Application-owned JWT authentication does not by itself implement an OIDC authorization server. The precise interoperability requirement is an open decision; do not claim OIDC conformance without the required protocol endpoints and tests.

### PAT — patient identity and consent (§§7, 33, 54–55)
- Validate required full name, birth date, gender vocabulary, phone, email and structured address. Supported demographic vocabularies and country-aware phone/address rules need approval.
- Uniqueness applies to verified identifier system + value within its documented issuer scope, not to a patient's name. Protect identifier values and use keyed lookup indexes where required.
- Shared family phone/email contacts are possible. Potential matches require restricted human review, not automatic merging, rejection or disclosure of another patient's details.
- Insurance failure must persist the patient with PENDING insurance status and an auditable follow-up, not rollback a valid intake solely because the provider is unavailable.
- Consent absence is not consent. Clinical access must evaluate an approved lawful-purpose policy; emergency/legal care bases cannot be invented or reduced to a blanket consent flag.
- Soft deletion does not satisfy every legal erasure request and does not remove clinical retention duties; policy and legal hold must be established before purge jobs exist.

### SCH — scheduling (§§8, 14, 31–32)
- Persist aware timestamps in UTC plus facility IANA timezone context. Reject nonexistent/ambiguous local times unless the caller provides an explicit offset and validated timezone.
- Validate start < end, permitted duration, availability, actor authority and doctor/facility membership server-side.
- Use PostgreSQL range exclusion for all appointments occupying a doctor's time, not just unique start times or application prechecks. Doctor identity should prevent cross-facility double booking when it is the same clinician.
- Two simultaneous overlapping bookings on separate connections must yield one success and one conflict, never two committed appointments. Audit/outbox/idempotency results share the winning transaction.
- Conflict response contains only authorized available alternatives in a defined approximately ±2-hour window; empty alternatives is a valid outcome. Duration, timezone and search-window semantics need explicit contracts.
- Emergency intake is not permission to overlap a named doctor's booked time. Triage/queue/escalation and authorized clinician assignment require an approved emergency workflow.
- Cancellation/reschedule append status history and invalidate superseded reminders. Recheck appointment state and timing before asynchronous delivery.

### REC — clinical information (§§9–10, 24, 31–32)
- Original record payload structures have not been supplied. DIAGNOSIS/PRESCRIPTION/LAB_RESULT/VISIT_NOTE discriminators are required; field-level contracts, code systems, units, authorship, signing and amendment rules remain unapproved.
- Successful plaintext release requires authorization and a durable access audit. Read paths, list paths, downloads, history and exports must all be covered; test audit-write failure blocks release.
- Update is a version-qualified compare-and-swap. Exactly one of two simultaneous updates to the same version succeeds; the other returns 409. Preserve prior encrypted content and authorship.
- Use authenticated AES-256-GCM with per-object data keys, unique nonces, authenticated tenant/resource/version context, and externally managed wrapping keys. Never log plaintext or key material.
- Application database credentials cannot update/delete audit events. SQL privileges/triggers must enforce this independently of router behavior. Infrastructure administrators remain an explicit tampering threat requiring external retention and review.

### FIN — financial correctness (§§14–16, 47–48)
- Monetary amounts use exact decimals with currency-specific precision, never floating point. Currency, payer billing standards, refunds, overpayment and tax rules require approval.
- Invoice creation has a business uniqueness rule and request idempotency. A new random key must not bypass duplicate-encounter/service protection.
- Scope idempotency by authorized actor/organization + operation; bind key to canonical request digest. Same key/different payload → 409. Never return a stored response before current authorization is checked.
- Lock financial aggregates or enforce equivalent serializable rules during settlement. Provider event ID is unique; verify signature, replay window, provider account, invoice, amount, currency and authoritative settlement status.
- Browser redirects never settle invoices. No raw PAN/CVV in API inputs, database, logs or exports.
- Provider timeout after sending is ambiguous, not confirmed failure. Reconcile using provider idempotency/status rather than blindly repeat a charge or claim.
- “Three retry attempts” is unresolved: three retries after the initial call versus three total attempts. Keep this explicit until the insurer contract is approved; PENDING_RETRY must not imply successful submission.

### ASYNC — durable side effects (§§17, 31, 47–49)
- Write outbox events with domain/audit writes in one PostgreSQL transaction. A committed outbox can recover after Redis loss; a rolled-back transaction cannot send a notification.
- Delivery is at-least-once; consumer keys and provider idempotency/reconciliation prevent avoidable duplicate side effects. Do not claim exactly-once external delivery.
- Separate pending/sent/failed/provider-confirmed-delivered states; “sent” is not proof a patient received a message. Avoid PHI in email/SMS bodies.
- Real providers remain unavailable until selected and configured. Test-only mocks never silently activate in staging/production.

### AI — clinical governance (§§18–22, 88)
- No source model, training data, clinical validation or approved red-flag rules were supplied. Do not invent a model or diagnostic performance to populate the UI.
- Require exact model artifact digest, feature schema, dataset lineage, approval identity, approval state, validation evidence and immutable version pinning.
- Default to inference unavailable if no approved model exists; do not fabricate confidence/alternatives. The normal prediction response contract applies only to a real, authorized, approved prediction.
- Clinician-approved red-flag handling can override an ordinary result. Failure to detect a red flag must never be presented as ruling out an emergency.
- Audit inputs/results as sensitive clinical information under retention/access/encryption policy, not ordinary request logs. Log rejected/failed requests without unnecessary symptom disclosure.
- Display exactly: “This tool provides informational decision support and does not provide a medical diagnosis. Clinical decisions must be made by qualified healthcare professionals.”

### OPS — proof and release (§§34–35, 40–43, 74–78, 94–99)
- Integration tests use PostgreSQL, never SQLite substitutes for exclusion, locking or isolation behavior.
- Every mandatory scan/test failure blocks promotion. Build once and promote the verified immutable image digest. Staging and production require separate configuration, approval and evidence.
- Neither passing tests nor a working dashboard establishes legal compliance, accessibility conformance, clinical validation or production readiness.
- RPO/RTO, retention, target load, maximum token-revocation delay and facility-sharing policies are stakeholder-approved targets, not guarantees supplied by this document.
- Restore drills must include encrypted DB/WAL, document objects and access to retained wrapping-key versions; exercise ransomware and credential compromise separately from simple infrastructure loss.
- No deployment command can be described as verified before the staging platform, access boundaries and execution results are known.
